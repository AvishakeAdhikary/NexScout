# ADR-0015: Real opportunity sources (provider adapters, catalog, custom sources)

- **Status:** accepted (M15, 2026-10-19)
- **Context:** Up to v2.1.0 the shipped product could search only three labelled demo
  fixtures. Users need real positions from company career pages (ATS), job boards and
  university portals across Europe. They also need to add sources NexScout doesn't know. The
  career-ops project (MIT) already maps about 110 boards and ATS APIs. Many boards forbid
  automated access, and some have no API at all.

## Decision
1. **Providers, not scrapers** (`integrations/sources/`).
   - Each provider implements `detect(url) -> config | None` and
     `fetch(http, entry) -> list[Job]` against a public, documented or widely used endpoint.
   - The endpoints and field mappings are ported from career-ops at commit
     `340a53b1bd4e9728237c6b964f3828589b1fc14e` (THIRD_PARTY_NOTICES.md).
   - There are 32 providers:
     - **ATS:** Greenhouse, Lever (US and EU hosts), Ashby, Workable, SmartRecruiters, Recruitee,
       Personio, Teamtailor, Breezy, Pinpoint, Rippling, Workday CXS.
     - **Boards:** Arbeitnow, The Hub, Landing.jobs, Just Join IT, Solid.jobs, No Fluff Jobs,
       Platsbanken (JobTech), Bundesagentur für Arbeit (jobsuche), Work in Finland, Getro VC
       boards, Remotive, RemoteOK, Working Nomads, Jobicy, Himalayas, 4 Day Week,
       We Work Remotely.
     - **Academic:** Varbi (Swedish universities); university Workday tenants.
     - **Generic:** RSS/Atom feeds and schema.org `JobPosting` JSON-LD pages.
2. **One fetch path.**
   - Every request goes through `infrastructure/fetch.SafeFetcher`, which handles:
     - SSRF pinning;
     - robots.txt: always checked for web pages, RSS/Atom feeds (including Varbi) and JSON-LD
       pages; skipped only for job APIs and ATS job feeds the publisher provides for machine
       reading (Personio XML, Teamtailor RSS, We Work Remotely RSS);
     - per-host pacing and size caps;
     - an honest user agent naming NexScout and its project URL.
   - `core.Http` adds a 400-request budget and HTTP→`SourceError` mapping. Each source is also
     capped at 25 pages and 2,000 postings.
   - The parsers treat responses as untrusted data: no DTDs in XML, HTML stripped to text, and
     only https posting URLs kept.
3. **Catalog** (`catalog.yaml`).
   - It is generated by `scripts/build_catalog.py` from upstream `portals.example.yml` and
     `SUPPORTED_JOB_BOARDS.md`, plus NexScout's EU, Finnish and academic additions.
   - There are 168 entries: 129 companies, 35 boards and 4 academic portals. Each entry carries
     its countries and kinds.
   - The file also records the upstream entries NexScout can't read, each with a reason (for
     example web-search entries that would need a paid search API), and the **manual-only**
     sites: Duunitori, Työmarkkinatori, EURAXESS, EURES, Academic Positions, AcademicTransfer,
     FindAPhD, LinkedIn, Indeed and Glassdoor. These are listed because their terms or
     robots.txt forbid automation, or they offer no public API. The UI shows them as "search
     on the site".
   - Catalog sources are **off until the user turns them on**.
4. **Custom sources** (`custom_sources`, owned, RLS).
   - Adding a URL checks it with `check_outbound_url`, then runs **detection**:
     1. provider URL patterns;
     2. ATS links found on a branded careers page;
     3. feed autodiscovery;
     4. JSON-LD.
   - It then test-fetches. Each user can add at most 300 custom sources.
   - A career-ops `portals.yml` can be imported. Entries already in the catalog are switched
     on, not duplicated, and unsupported entries come back with their reason.
5. **Health per source.** `source_configs.last_status/last_error/last_count/last_fetched_at`
   record every fetch. "Check" re-tests a source on demand. One failing source never stops the
   others: they are fetched in parallel, at most 6 at a time, with a 300 s timeout.
6. **Filtering before storage.** In `sync_case`, the case's search words, excluded words and
   included/excluded countries drop irrelevant postings before they are stored or matched.
   The sync summary reports how many were dropped.
7. **Demo data only on request.** The fixture sources and demo site are registered only when
   `NEXSCOUT_DEMO_DATA=1`, which the tests and E2E set. Production builds never show them.

## Consequences
- Real postings in production. Each source states where its data comes from, and its
  failures are visible as text the user can act on.
- Boards that forbid automation stay manual. NexScout never works around a 403, a sign-in or
  robots.txt.
- Upstream changes are pulled deliberately: re-run `build_catalog.py` against a new pinned
  commit and re-record the fixtures with `scripts/record_source_fixtures.py`.
- Replay tests (`tests/unit/test_source_providers.py`) run against trimmed real responses for
  all 28 network providers. Endpoint drift is caught by re-recording, not in CI. CI never
  calls third-party sites.
